## 1. 引擎选型

### 1.1 本项目的真实约束

选型不是选“最强引擎”，而是选**在这个需求组合下返工最少**的引擎：

1. Android 优先，中端真机 60 fps，必须能方便地读到 CPU/GPU/物理/GC 数据。
2. 像素美术、严格整数缩放、低分辨率渲染，不能被后处理糊掉。
3. 可破坏瓦片不是装饰，而是核心解谜与战斗手段；地形碰撞会持续被修改。
4. 200 级别碎片、连锁爆炸、坍塌体，要求物理和渲染都有可控的降级层级。
5. 打击感依赖逐帧控制：顿帧、震屏、慢镜头、镜头边界、动画和音效同步。
6. v0.1 只有 3 关，但要求 4 个手感差异明显的角色；工具链要能快速迭代数值。
7. 项目规模小，**不引入付费中间件、不引入 ECS、不做通用物理沙盒**；拒绝为“架构漂亮”付出首版成本。

### 1.2 Unity 2D vs Cocos Creator

评分仅针对本项目（5 分制，权重来自上面的约束）：

| 维度 | 权重 | Unity 6 LTS + URP 2D | Cocos Creator 3.x |
|---|---:|---:|---:|
| 可破坏瓦片 / 2D 物理可改造性 | 30% | 5 | 3 |
| 手机性能可测性与调优成熟度 | 25% | 4 | 3 |
| 打击感、镜头、粒子、动画工具链 | 20% | 5 | 3 |
| 小型项目迭代速度 | 15% | 3 | 4 |
| 安装包体 / 轻量分发 | 10% | 2 | 5 |
| **加权总分** | 100% | **4.15** | **3.35** |

**技术判断：**

- **Unity 赢在“可破坏地形 + 手感控制 + 性能可验证”这三件本项目的核心难点上。**
  - C# 编写编辑器工具（关卡烘焙、地形校验、配置导入、压力测试）效率高、类型安全。
  - 2D 物理底层成熟；我们最终仍会自研碰撞生成，但调试工具、Profiler、GC 观测和真机抓帧链路完整。
  - 粒子、动画、音频、镜头虽然部分要自研以保证像素对齐，但底层能力和社区经验充足，M3 打磨成本更可控。
- **Cocos 赢在安装包、TypeScript 迭代速度和国内发布链路。** 如果这是一个微信小游戏、或者团队只接受 TS、且没有复杂可破坏地形，Cocos 会更合适；但本项目核心卖点恰好压在可破坏地形与夸张物理反馈上，Cocos 需要自研的部分更多，且真机上定位性能尖刺的成本更高。
- **“引擎更大”不是问题，“不可控”才是问题。** 我们可以关闭 2D 灯光、后处理、Addressables、Timeline 等非必需模块，将 APK 和运行时开销控制在小项目范围；换引擎省下的安装包，无法弥补物理坍塌和手感返工的风险。
- 不选用内置 TilemapCollider2D 直接作为运行时方案，原因见第 3 节；Unity 只是提供开发与本项目自研两层碰撞的可靠底座。

**会让我改变结论的条件：**
- 分发目标改为微信小游戏且必须小包体；
- 团队完全没有 C# 经验，而核心人员可全职投入 Cocos；
- 实测 Unity 在中端目标机上即使做到 200 视觉碎片规整场景仍无法稳定 60 fps（目前判断不会）。
以上任一条件成立，再重开选型，不在中途反复切换引擎。

### 1.3 技术栈、版本与工程约束

| 项目 | 方案 |
|---|---|
| 引擎 | Unity 6 LTS；安装时取 Unity Hub 可用的最新 6.x LTS patch，并写入 `ProjectVersion.txt` 锁定 |
| 渲染 | URP 2D Renderer，Unlit；不使用 2D 动态灯光、Bloom、景深、运动模糊 |
| 脚本 | C#；Release 用 IL2CPP + ARM64；不使用 ECS/DOTS |
| 输入 | Unity Input System；触摸路由自研，虚拟按键 UI 只负责显示 |

### 1.4 Android 构建口径

- 安装包：APK；仅 ARM64，IL2CPP Release；另保留 Development Build 用于 Profiler。
- 最低系统：Android 8.0（API 26）；目标 API 在正式出包时按 Google Play 当期要求设置。
- 图形 API：**以 OpenGL ES 3 为基线**，目标机实测 Vulkan 有稳定收益再切换；不在未验证前引入 Vulkan 驱动风险。
- 刷新率：请求 60 fps；在 90/120 Hz 高刷屏上固定 60，避免速度与抖动变化。
- 分辨率：世界层低分辨率渲染；UI 用原生分辨率 Overlay Canvas，保证触控按钮和文字清晰。
- 安全区：以 `Screen.safeArea` 约束 HUD 与触控热区；刘海/挖孔不遮挡按钮。
- 包体：以 ≤ 100 MB 为初版目标；实际以内容完成后测量，不为了压包牺牲原创音频与可读性。

### 1.5 本机环境现状（必须前置处理）

已在工作区做只读检查：目录为空；本机未发现 Unity Hub/Editor、Cocos Dashboard、Android Studio/SDK，`ANDROID_HOME` 未设置；已有 Node.js、Java 25、Visual Studio 2022、Git、约 1.4 TB 的 E 盘空间。建议 Unity 与 Android SDK 安装在 E 盘。

**M1 开始前需要完成：**
1. 安装 Unity Hub 与 Unity 6 LTS，勾选 Android Build Support（含 SDK/NDK/JDK）；
2. 登录 Unity 账号并确认授权条款；工程不依赖任何付费包；
3. 安装 Android 平台工具，确认 `adb devices` 能看到真机；
4. 提供至少一台 1080p、60 Hz、Android 12+ 的中端真机作为性能基线；
5. 确认允许下载/安装上述工具链（预计十几 GB，视版本而定）。

Android 构建优先使用 Unity Hub 随附的 JDK/NDK/SDK，避免用本机 Java 25 直接跑 Gradle 的兼容性风险；系统 Java 只用于独立小工具时再单独指定。

**这不是技术风险，而是排期前置条件。** 环境未就绪时，M1 的一周窗口承诺不成立。

### 2.2 更新与权威数据

- 物理/角色移动：`FixedUpdate`，固定 60 Hz；渲染帧率目标 60。
- 输入采样：`Update` 最早阶段读取并缓存；UI 只显示；触摸拥有权按 pointerId 管理。
- 目标：**输入到画面反馈 ≤ 2 个渲染帧**；不使用固定输入延迟。
- 地形权威：内存中的 `TerrainGrid`，不是 Collider 的实时状态。子弹、爆炸、坍塌判定都先查网格，再同步碰撞体，避免“碰撞体晚一帧导致穿墙/打不中”。
- 对象池：子弹、碎片、粒子、音源、敌人尸体、伤害飘字全部池化；稳态运行不产生常规 GC。
- 所有随机效果使用可注入种子的伪随机（战斗表现可回放测试），但不做确定性联网模拟。
- 只在 White-list 事件里设置慢镜头；`TimeDirector` 拒绝普通击杀来源，开发构建记录违规日志。

## 3. 可破坏地形：方案对比与定案

### 3.1 备选方案

| 方案 | 表现力 | 物理/更新时间 | 手机风险 | 开发成本 | 结论 |
|---|---|---|---|---|---|
| A. Unity Tilemap + TilemapCollider2D/CompositeCollider2D 直接破坏 | 瓦片感好，破坏边界方正 | 每次 SetTile 引发局部 Tilemap/Collider 更新；大量修改时尖刺难控 | 中 | 低 | 只用于**关卡编辑**，不作运行时碰撞权威 |
| B. 位图可破坏 + Marching Squares 重建碰撞 | 不规则孔洞最细腻，爆炸边缘好看 | 轮廓重建、三角剖分和碎片切分都重；碰撞体易碎 | 高 | 高 | 不作为 v0.1 核心地形 |
| C. 网格切片 / 凸多边形切分 | 适合可破坏掩体、平台 | 每次切割生成新多边形，数量增长快 | 中高 | 中高 | 可局部用于大块掩体，不做整张地图 |
| D. 每块瓦片一个 Rigidbody | 坍塌最直观 | 几百刚体 + 碰撞对，物理和 GC 不可控 | 高 | 低 | 禁止 |
| E. **自研分块瓦片网格（推荐）** | 方正像素边界，配合碎块/烟尘足够爽 | 只重建受影响块；碰撞合并为矩形；坍塌单独处理 | 低~中 | 中（M1 的核心工作量） | **采用** |

### 3.2 定案：分块瓦片网格

**分层职责：**

1. **编辑层**
   - 使用 Unity Tilemap + 自定义 TileBase 作为灰盒/正式关卡画笔。
   - 每块瓦片只承载：材质 ID、耐久、是否结构支撑、是否可坍塌。
   - Play 前或打包前烘焙成关卡数据：`width × height` 的 `TerrainGrid`；运行时不再依赖 Tilemap 渲染。
2. **权威数据层**
   - `TerrainGrid` 保存材质/HP/空实心/锚定标记。
   - 所有弹道命中、爆炸挖除、支撑判定先作用于网格。
3. **渲染层**
   - 地图按 **16×16 瓦片分块**，每个 chunk 生成一张合并 Mesh；只在实际发生破坏时重建对应 chunk。
   - 每个 chunk 一次 draw call；480×270 画面通常同时只可见 2×2~4×2 个 chunk，渲染压力极低。
   - 碎块、边角粉尘走独立碎片系统，不进入 chunk Mesh。
4. **碰撞层**
   - 每个 chunk 生成**贪心合并的矩形 BoxCollider2D**，挂在静态 Rigidbody2D 下。
   - 只重建脏 chunk；每帧最多处理 2 个 chunk 的碰撞重建，剩余进队列。通常一次爆炸只影响 1~4 个 chunk。
   - 不在每格放 Collider，避免数百个 collider 和反复同步。
5. **表现层**
   - 网格被挖空 → 立即更新 chunk Mesh，生成尘/碎屑；碰撞在当帧或下一帧跟上。
   - 坍塌体转为动态刚体块，复用独立的 T0 碎片预算。

**16×16 分块的理由：**
- 480×270 约为 30×16.9 格，视口内 2~4 个 chunk，粒度足够细；
- 单个爆炸半径通常 2~3 格，不会一次弄脏整张图；
- 单 chunk 最多 256 格，贪心矩形和 Mesh 重建都可控；
- 跨 chunk 的连通性由全局 SupportSolver 处理，不受分块限制。

### 3.3 破坏生命周期

```text
武器命中 / 爆炸
  → 网格查询（DDA 射线或圆形范围）
  → 扣减 HP / 立即挖除可爆瓦片
  → 标记 dirty chunks（渲染 + 碰撞）
  → 触发支撑图增量检查（节流）
  → 生成碎屑 / 小爆点
  → 链爆队列检查油桶/弹药箱
  → 在 LateUpdate 限预算刷新 Mesh / Collider
```

- 步枪：单发可削薄泥土，对混凝土效率低，对钢几乎无效；让“用枪打洞”存在但不替代爆破。
- 手雷/榴弹：按半径挖除；坚固材质需要更高伤害；越靠近爆心挖得越干净。
- 下压砸地：小范围震荡伤害，可砸裂薄地板，但不如手雷高效。
- 延迟刷新碰撞体：避免在物理回调中改 Collider 造成不确定行为；同一帧内玩家脚下被炸空时，下一物理步自然下落。

### 3.4 支撑与坍塌（“炸塌平台埋敌人”）

**规则：**
- 以 4 邻接实心格构建连通块。
- 连通块与地图底边连通，或包含“锚定”格，则视为有支撑。
- 破坏导致连通块失去全部支撑时，进入 `PendingCollapse`，先给 **0.15~0.25 s** 的抖动/裂纹/音效预警，再转为动态坍塌体。
- 坍塌体按大小、质量获得向下加速度与轻微扭矩；碰撞到敌人时造成即死或高额碾压伤害；对玩家造成伤害并给短暂无敌，避免不可读的瞬杀。
- 坍塌体落到地面或障碍后停止物理模拟，保留 2~4 s 后淡出并还原为静态地形或碎屑。

**防失控：**
- 单次坍塌最多生成 12 个全物理块；超出拆成视觉碎块，不增加物理体。
- 支撑求解按脏区增量、100 ms 节流；关卡加载时做一次全图校验。
- 禁止“全图连续坍塌”作为常规设计手段；M1 只验证一座桥/一块高台。
- 支撑图只决定“是否掉落”，不做真实结构应力；这是为了可读性和性能，不是物理仿真器。

**两个涌现玩法在关卡中的落点：**
1. **炸穿地面开路**：教学关地下通道上方是 3 格薄地板，玩家用手雷或串爆油桶打通；掉落敌人可被下方敌人/尖刺接住（后续关卡）。M1 必须可复现。
2. **炸塌平台埋敌人**：高台由两根可破坏支柱或与墙体的连接格支撑，敌人站在下方。打断支撑后平台整体坠落，压扁敌人；坍塌体再作为临时掩体/地形。M1 必须可复现。

### 3.5 连锁爆炸

- 油桶与弹药箱是 `ExplosiveProp`：有 HP、被弹道/爆炸伤害触发。
- 爆炸触发后进入全局链爆队列：
  - 同一物体只爆一次（id + chainId 去重）；
  - 引爆半径内的其它爆炸物延迟 **0.08~0.15 s** 入队，形成可读的“接力”节奏；
  - 单帧最多处理 8 次引爆，单条链最多 24 个物体；
  - 震屏使用“最大优先、不可无限叠加”策略，避免 24 连爆把画面晃吐。
- 油桶与弹药箱参数不同：油桶半径更大、击飞更强；弹药箱碎片更多、链半径略小。两者都能被枪打爆，形成玩家主动设计的多米诺。

### 3.6 碎片分级与 200 碎片的实现

“同屏 200 碎片”在本项目中定义为：**屏幕上同时存在且逐帧被模拟/渲染的碎片对象 ≥ 200**。为了保证 60 fps，采用三级预算，而不是 200 个全刚体：

| 层级 | 对象 | 预算 | 碰撞/物理 | 生命周期 |
|---|---|---:|---|---|
| T0 | 大地形坍塌块、半个平台 | ≤ 12 个 Rigidbody2D | 与地形碰撞，造成碾压伤害 | 2~4 s，之后淡出 |
| T1 | 小石块、油桶碎片、尸体零件 | ≤ 40 个 Rigidbody2D | 只与地形碰撞，不与彼此碰撞，不与角色产生物理推挤 | 1.5~3 s |
| T2 | 细碎粉尘/碎屑 | 补足到 **200+** | 单个合并 Mesh，自研轻量抛物线 + 网格点碰撞，无 Collider | 0.6~1.6 s |

- T2 在单个动态 Mesh 中用 200 个 quad 绘制，一次 draw call，控制 CPU 更新与顶点写入；不使用 200 个 GameObject/SpriteRenderer。
- 所有碎片不参与角色碰撞；对敌人的伤害通过爆炸/坍塌事件显式结算，避免 N² 碰撞对和不可预测推挤。
- 在 M1 压力场景中额外做一组“纯 T1 200 刚体”实验，仅用于测上限和写报告，不作为常规配置。
- 这样定义的 200 碎片仍是物理响应：被炸飞、落地弹跳、旋转、逐渐消失；区别只在碰撞精度和对象层级。

> **需要确认的验收口径：** 如果你要求“同屏 200 个带 Collider 和 Rigidbody2D 的独立碎片也稳定 60 fps”，这是另一条性能门槛。M1 会实测并给出真实上限，不会用视觉伪装冒充。若必须 200 全刚体，渲染层可做到，但物理/脚本预算会显著上升，可能需要降低其它同屏对象。

### 3.7 已知限制（明确写出来）

- 不做逐像素挖洞（只有 16×16 网格边界）。
- 不做真实结构力学；坍塌规则是“连通+锚定”的可控近似。
- 不支持斜坡/半砖碰撞；全部轴对齐方格。
- 坍塌中的平台不保证能稳定承载玩家；M1 关卡会避免让玩家站在会塌的平台上解谜。
- 这套实现是“可读、可控、可调”的动作游戏地形，不是 Terraria/Noita 式沙盒。

## 4. 操作、自动瞄准与角色

### 4.1 触屏布局

```text
横屏
┌───────────────────────────────────────┐
│ HUD / 关卡目标                  暂停  │
│                                       │
│                 游戏安全区            │
│                                       │
│                                       │
│    ◯ 左摇杆          [手雷]           │
│                  [跳]    [射击]        │
└───────────────────────────────────────┘
```

- 左摇杆：左下安全区，固定基座，死区 0.18，径向响应曲线；拖动越远移动越快。
- 右三键：射击为主键，尺寸最大；手雷在上方，减少误触；跳跃紧邻射击，便于右手滑动。
- 触控热区比视觉图形大约 15~25%；按钮按下状态用亮度/缩放反馈。
- 多指同时按压必须稳定；输入按 pointerId 独立追踪。右手从跳跃滑向射击不能丢失按压。
- 编辑器/PC 调试键位另设，不影响手机布局。
- 触控 UI 用 1080p 参考尺寸 + `Screen.safeArea`/dp 换算；具体按钮物理尺寸以 ≥ 10 mm 触控目标为底线，在 M1 真机调。

### 4.2 8 向射击 + 自动瞄准

“8 向”定义在**输入、姿态和 UI**：玩家的射击意图始终归入 8 个 45° 扇区，角色枪口动画只有 8 个方向，自动瞄准负责**选目标和选扇区**。弹道分两种情况：

- **没有锁定目标**：严格沿扇区中心（0°/45°/90°…）发射。
- **锁定目标**：允许在当前 45° 扇区内朝目标方向收敛（最多 ±22.5°），保证在 10 格外不会因为“死守 45°中心线”必然打空；绝不跨扇区、不反向拐弯、不穿墙、不做制导追踪。

这是为了避免“看起来是自动瞄准、实际子弹从敌人旁边擦过”的假硬核。锁定时的拖尾会显示真实落点，玩家仍能用 8 向控制意图。

目标选择规则：
1. 候选：当前画面内、在射程内、有视线（地形 DDA 不穿墙）的敌人、Boss 弱点、可爆物。
2. 优先方向：
   - 摇杆推动 ≥ 0.35 时，以摇杆方向为首选；
   - 摇杆居中时，以角色朝向为首选。
3. 评分：距离 + 角度偏差惩罚 + 目标类型权重；Boss 弱点优先，可爆物在无敌人时可用。
4. 对当前目标保留 0.12 s 迟滞，避免两个敌人来回跳准；目标死亡/出视线/超时立即释放。
5. 先把目标方向归入 8 向扇区；锁定时弹道在该扇区内向目标中心收敛，并显示极简准星/扇区高亮，告诉玩家系统选中了谁。
6. 目标不在任何合理扇区时不强行吸附；没有目标时就按扇区中心打，允许打空，避免“魔法回头弹”。
7. 射线/弹道总宽 2 px，弥补像素级碰撞与真实目标中心之间的误差。

为什么不加右摇杆：需求明确要求“三键 + 自动瞄准”。再加右摇杆会和手雷/射击争夺同一个拇指，手游上比 8 向辅助更糟。M1 会用“射击移动靶”来验证这套方案是否成立；如果通不过，优先改辅助曲线，而不是加第四根摇杆。

手雷是抛物线投掷，不吸附目标：它只继承当前的 8 向意图，按固定弧线/初速抛出；首次接触地形或敌人后 0.15 s 短引信起爆，未接触则 1.2 s 自爆。这样玩家能主动把雷丢到脚下/墙上拆地形，也不会出现“魔法跟踪雷”。后续火漆的榴弹筒是否做弹道辅助，在 M2 单独验证，但同样不做制导。

### 4.3 近战、下压跳与三键约束

- **近战小刀（按追加要求整改）**：自动接近触发，不消费射击/手雷输入。
  - 当普通敌人进入 1.15 格自动近战半径时，显示世界环形半径提示，并播放一次 tick 音效；出刀本身触发 2 帧 hitstop。
  - **只要 FireHeld / FirePressed / GrenadeHeld / GrenadePressed 任一成立，就不自动出刀**；近战也不会替代、拦截或消耗射击/手雷指令。这样不存在“想开枪/扔雷却误出刀”的输入路径。
  - 出刀函数内再断言一次武器意图，防止未来改代码时回归。
  - 敌人被小刀命中的白色刀光、音效、2 帧 hitstop 同时存在，满足“明确触发反馈”要求。
  - 忍者“纸鸢”将该自动近战半径扩展为 3.4 格内的瞬移斩，并带 0.2 s 无敌帧；见角色表。
- **下压跳**：空中按住摇杆下 + 按跳跃 → 快速下砸。落地产生范围冲击、轻微地形损伤、震屏和命中停顿；不是慢镜头。
- **跳跃**：可变高度、土狼时间 0.10 s、跳跃缓冲 0.12 s；只在落地/离地边缘做宽容，不使用自动跳。
- 不为近战、下压跳、换人新增第四/第五个动作键；所有额外动作都必须能映射到“摇杆 + 三键”。

### 4.4 四名角色（v0.1 验证矩阵）

| 角色 | 定位 | 独立主武器 | 标志性机制 | 解锁 |
|---|---|---|---|---|
| **弹簧**（步枪兵） | 均衡/新手 | S-3 三连钉：紧凑的 3 发点射 | 第三发过载：每轮第三发 +50% 伤害并贯穿 1 个目标，鼓励有节奏地跟枪 | 初始 |
| **火漆**（爆破手） | 拆地形/爆发 | 双响榴弹筒：接触爆炸，溅射范围大 | 每发榴弹“双响”：0.18 s 后二次小爆，挖地形最快，也更容易串爆 | 第 1 关救人质 |
| **门闩**（霰弹哥） | 贴脸/位移 | 双管霰弹：7 颗弹丸、近距离高爆发 | 后坐力跳：空中开枪获得反向推力，可借枪跳上高台/脱离包围 | 第 2 关救人质 |
| **纸鸢**（忍者） | 机动/切入 | 袖针：高速单发贯穿飞针 | 二段跳 + 瞬移斩：近中距离情境出刀，突进穿敌并有短无敌 | 第 3 关救人质 |

说明：
- 每人都有共用动作：移动、跳、下压砸、情境小刀、手雷；差异来自主武器 + 一个签名机制，不额外堆按钮。
- 角色名称与武器名均为暂定原创工作名，正式上架前做商标/关键词排查。
- M1 只实现“弹簧”的移动、三连射、情境刀、下压跳，用于验证基础身体手感；其它三人不进入 M1 代码范围。

### 4.5 人质解锁流程

- 四名角色中“弹簧”为初始角色，其余三名通过关卡内人质救援解锁。
- 第 1 关中途救出火漆，第 2 关救出门闩，第 3 关救出纸鸢。
- **救援后立即换上被救角色**，剩余路段专门设计一个展示其机制的短段；避免“刚解锁就没机会用”。
- 关卡结算后，已解锁角色可在关卡开局选择。进度用本地 JSON 保存，不接账号、不联网。
- 人质不进入护送 AI；救出即完成交接，避免额外寻路与关卡破坏后的跟随 bug。

## 5. 关卡与 Boss/逃亡流程

> 本节只锁结构与技术钩子；精确房间尺寸、敌人配置和镜头节奏在 M2 制作前另出关卡文档并再次评审。

| 关卡 | 定位 | 时长目标 | 核心教学/验证 | 结尾 | 救援 |
|---|---|---:|---|---|---|
| 1. 卸货口 | 教学关 | 70~90 s | 移动、跳跃、8 向射击、手雷、情境刀、炸穿薄地板 | **逃亡**：后方压包墙推进 + 限时穿仓 | 火漆 |
| 2. 矿料仓 | 破坏教学关 | 90~120 s | 链爆油桶、炸塌高台压敌、坍塌地形改变掩体 | **Boss：冲压机**（摧毁支撑让机器砸毁自身） | 门闩 |
| 3. 信号塔 | 混战关 | 100~120 s | 全机制混合、连续的“爆破→铺路→换掩体” | **Boss：塔长**（破坏吊臂/配重，最终 Boss 慢镜头） | 纸鸢 |

- 每关 1~2 min，目标以首次通关时间为准；中途设 1 个检查点，避免手机端失败后重打全关。
- 逃亡段不触发慢镜头；仅在逃脱成功结算瞬间触发通关慢镜。
- Boss 关的 Boss 死亡慢镜与通关结算合并成一段，不连续触发两次；细节见 6.2。
- Boss 和敌人全部原创；只借鉴“横版跑打 + 可破坏场景”的类型语言，不复刻现有关卡布局或角色造型。

### 5.1 逃亡关技术

- 追逐墙以恒定速度推进，路面/后方地形按脚本挖除并生成碎屑。
- 失败条件：被墙追上；死亡后回到检查点，追逐墙重置到安全距离。
- 无过场 CG；开场用 1 行目标 HUD + 音效提示，逃亡全程保持可操作。
- 镜头锁定前方、不自动旋转；震动只在墙体撞碎结构时触发。

### 5.2 Boss 技术

- 每个 Boss 是一个显式状态机：Intro → Phase 1 → Transition → Phase 2 → Death；不写通用行为树。
- Boss 血条仅在 Boss 激活后出现；死亡触发 FeelDirector 的 `BossDeath` 白名单事件。
- Boss 本身可受地形影响：第 2 关的最终伤害来自坍塌的冲压机，而不是纯子弹血条；让“拆地形”是解题手段。
- Boss 攻击预警优先用形状/颜色/音效，不依赖小字提示。

## 6. 像素渲染与爽感演出

### 6.1 分辨率与屏幕适配

- 基准世界分辨率：**480×270**，美术按 16×16 瓦片设计；1 单位 = 16 px。
- 常规游玩：世界渲染到低分辨率 RenderTexture，以**整数倍**点采样放大；UI 用原生分辨率 Overlay，不跟着像素化，以保证文字和按钮清晰。
- 16:9 设备显示完整 480×270 安全区。
- 更宽手机（18:9/20:9）：保持同样的“1 艺术像素 = 整数屏幕像素”，在 **480×270 安全区左右增加可见列**。例如 1080p 20:9 可显示约 600×270；关卡关键路径全部位于 480×270 安全区内。这样既不拉伸、不模糊，也不把两侧全变成黑边。
- 16:9 720p 设备：2 倍整数放大为 960×540，会有上下/左右黑边；这是为统一像素网格和原生 UI 做的取舍。中端 1080p 是验收基线；720p 只做兼容性冒烟，不作为 60 fps 性能承诺机型。
- 世界里所有可见 Sprite 在 LateUpdate 做 1/16 单位像素吸附；相机也吸附，避免慢速移动时抖动。
- 不使用动态分辨率、FSR、TAA；像素游戏不需要，也无法保证网格稳定。

**相机推近的像素约束：**
- 常规游玩与外景震屏始终整数缩放。
- Boss 死亡推近只在 0.5~0.8 s 的非交互演出窗口启用，采用“更大整数倍裁切放大”的离散档位（例如 4× 全画幅 → 5× 裁切），用短暂闪白/构图遮挡跳变；不做连续非整数缩放。这样严格守住像素网格。
- 如果评审更看重顺滑推近而非严格整数，我们才改用短暂非整数缩放，并承担轻微像素抖动；默认不这么做。

### 6.2 慢镜头白名单（硬约束）

| 事件 | 触发 | 时间缩放 | 真实时长 | 镜头 | 普通击杀是否允许 |
|---|---|---:|---:|---|---|
| Boss 死亡 | 仅 `BossDeath` 事件 | 0.15~0.25 | **0.50~0.80 s** | 推近 + 6 px 震屏 + Boss 定格 | 否 |
| 通关/逃脱成功 | 仅 `LevelClear` 事件 | 0.35 | 0.45~0.60 s | 轻微推近，然后结算 UI | 否 |
| 普通小兵死亡 | — | 1.0 | — | 2~3 帧 hitstop + 1 px 震屏 + 血花/碎块 | **禁止** |
| 玩家死亡/受伤、爆炸、连杀 | — | 1.0 | — | 冲击反馈，可震屏 | **禁止** |
| Boss 死亡且立即通关 | 合并为 BossDeath 一段 | — | 不再叠加 LevelClear | — | 否 |

实现方式：
- 所有慢镜头必须调用 `FeelDirector.RequestSlowMo(Reason.BossDeath | Reason.LevelClear)`；其它枚举值编译期不存在。
- UI、音频淡入淡出、debug overlay 使用 unscaled time，不被慢镜头影响。
- 输入在 Boss 死亡演出期间锁住，防止角色在镜头里乱跑；演出结束恢复正常。
- 慢镜头期间低通/降调只作用于音效总线，音乐保持节拍或柔和降速，M3 调。

### 6.3 Hitstop 与震屏

**普通击杀反馈包：**
1. 命中瞬间：敌兵白闪 1 帧、碎块/血花粒子、短促命中音。
2. 击杀瞬间：全局 hitstop **2~3 帧 @60 fps（约 33~50 ms）**；同时多杀合并成一次，取最大值，不叠加。
3. 震屏：1 px 幅度、约 0.07 s、45 Hz 衰减噪声；不进入慢镜头。
4. 枪口反馈：1~2 帧 muzzle flash、弹壳（轻量碎片）、轻微相机后坐。
- 连续射击时 hitstop 有 0.1 s 冷却，避免霰弹一次杀 3 个导致长时间卡顿；只对击杀触发，不给每次擦伤都顿帧。

**震屏分级（全部外置，首版值见第 8 节）：**

| 等级 | 来源 | 基础像素幅度 | 时长 | 频率 | 规则 |
|---|---|---:|---:|---:|---|
| S0 | 普通命中/小刀 | 1 px | 0.04~0.06 s | 45 Hz | 仅反馈；同一目标 0.08 s 内不重复触发 |
| S1 | 普通击杀 | 1 px | 0.07 s | 45 Hz | 高频但轻 |
| S2 | 手雷/单桶爆炸 | 2 px | 0.12~0.16 s | 40 Hz | 同帧多爆炸取最大 |
| S3 | 大范围链爆/坍塌落地 | 3 px | 0.18~0.25 s | 35 Hz | 链爆不按个数叠乘 |
| S4 | Boss 死亡 | 6 px | 0.60~0.75 s | 22 Hz | 仅 BossDeath |
- 使用噪声/衰减曲线而非随机每帧白噪，防止看起来像画面撕裂。
- 震屏偏移取整到基础像素，避免低分辨率画面出现半像素抖动。
- 支持设备“轻触觉反馈”仅作为可选开关（M3），默认不影响玩法。

### 6.4 敌人物理喜剧化

- 敌人有轻量受击刚体：被爆炸击飞时获得径向+向上偏置的冲量，外加旋转；空中挤压/拉伸 1~2 帧，落地弹 2~3 下。
- 被坍塌体压中：切换为扁平贴图残影，播放“噗”的音效，短震屏；尸体不参与后续碰撞，避免关卡被尸体堵住。
- 尸体用 T1 预算，最多 12 具同时物理化，超过转静态贴花；尸体 3~5 s 清理。
- 物理夸张但规则可读：击飞方向始终可预测为“远离爆心 + 向上偏置”，不加入随机水平大反转。
- 不对玩家做同等夸张的布娃娃，玩家受击用明确击退+无敌帧，避免失控坠落造成挫败。

### 6.5 枪感/打击感清单

每个武器必须有：
- 开火前的蓄力/后坐预备（1~2 帧）；
- 枪口火舌、弹道拖尾/弹丸、弹壳；
- 命中粒子和材质差异（泥、混凝土、金属火星），音效分层；
- 击杀额外 hitstop/震屏/碎片；
- 自动瞄准的“选中目标”反馈；
- 空仓/冷却反馈（枪口冒烟、按钮变暗），不靠文字说明。
- 所有数值不在代码常量里，统一进配置表。

## 7. 性能目标与验收方法

### 7.1 目标机与预算

**基线机：红米 Note 12（或同等级天玑/骁龙中端、1080p、60 Hz、Android 13）。** 允许先用云真机跑第一轮趋势，但最终 Go/No-Go 必须在用户指定的物理真机上复测；不使用模拟器结果验收。

60 fps 的单帧预算为 16.67 ms。工程目标把主线程压到 **≤ 13.8 ms**，留出 ~2.8 ms 给系统抖动/热降频：

| 项目 | 目标预算（95 分位） |
|---|---:|
| 脚本（Gameplay/AI/输入/UI） | ≤ 3.8 ms |
| 2D 物理 + 碰撞同步 | ≤ 2.5 ms |
| 渲染提交（CPU） | ≤ 2.8 ms |
| 碎片/粒子更新 | ≤ 1.2 ms |
| GC/杂项 | ≤ 0.7 ms |
| 硬件/系统抖动余量 | ≥ 2.8 ms |

物理/碎片硬上限：
- T0 地形坍塌体：≤ 12 个动态 Rigidbody2D；
- T1 小碎片/尸体：≤ 40 个动态 Rigidbody2D；
- T2 轻量碎片：同屏补足至 **≥ 200 个可见碎片**；
- 单帧链爆处理：≤ 8 个；单链总数：≤ 24；
- 脏 chunk 碰撞重建：≤ 2 个/帧；Mesh 重建 ≤ 2 个/帧；
- 稳态 GC：≤ 1 KB/帧，池化系统预热完成后不允许明显分配。

### 7.2 测量方法与门槛

- 使用 Development/Release 对比、Unity Profiler（USB）、设备 log/CSV、`ProfilerRecorder` 采集：
  - 平均 FPS、1% low、0.1% low、最大帧时间；
  - 主线程脚本/物理/渲染、GC Alloc、draw call、活跃碎片/刚体数；
  - 每 10 秒自动记录一次，导出 CSV；
  - 连续 10 分钟热稳定性循环，记录温度/降频后的帧率。
- 标准压力场景：
  1. 空旷场景基线；
  2. 10 敌人交火 + 自动瞄准；
  3. 一次事件生成 200 碎片 + 12 坍塌块 + 3 连爆；
  4. Boss/大范围坍塌混合；
  5. 10 分钟循环。
- 录制 60 fps 或更高帧率的真机演示，避免只给“平均 60”。
- **Profiler 只用于 Development Build 的逐系统拆解；对外验收的 FPS 必须来自 Release Build 的游戏内 CSV。** 两者都记录，但不把 Development 的开销当成最终帧率。
- 验收（M1 先测，M3 最终复核）：
  - 基准机 1080p，压力场景 **平均 ≥ 59 fps、1% low ≥ 54 fps、无单帧 > 33 ms**；
  - 正常游玩平均 ≥ 59.5 fps；
  - 10 分钟热稳定后平均 ≥ 57 fps、1% low ≥ 50 fps；
  - 200 可见碎片全部存在时达到上述门槛；
  - **全刚体 200 是 P5 实验：照做、写入报告、作为 M3 优化余量参考，但不计入 M1 Go/No-Go**；不得把它的失败当作 P4 的替代或掩盖。
- 如果未达标：先按顺序降级 T1 刚体数量→减少粒子/碎片存活时间→优化 chunk 重建；**不允许偷偷降低视觉碎片计数后仍宣称 200**。
- **数据真实性红线：性能 CSV 必须来自真实运行帧；宁可 No-Go，不允许编造/选择性只报最好一轮。**

### 7.3 性能设计预防措施

- 不在每帧做 `FindObjectsOfType`、LINQ、字符串拼接、闭包分配；查询用 `NonAlloc`/预分配列表。
- 所有子弹、碎片、粒子、音源、敌人、尸体池化；预热发生在加载画面。
- 物理层碰撞矩阵收窄：碎片只与地形碰，彼此不碰；角色使用自定义运动学 BoxCast，不依赖动态刚体。
- 只对可视区/近区生成复杂特效；离屏敌人和碎片停止表现更新，但不影响判定。
- Canvas 拆成静态 HUD 与动态虚拟键两层，避免整块重建；关闭不需要的 Raycast Target。
- 使用单一材质贴图图集；碎屑一个 Mesh 一次提交；不外挂大量小脚本 Update。
- 进度/配置从本地加载一次，不在战斗中读盘。

## 9. 内容生产与工具链（M2 起）

- 关卡：Tilemap 画笔绘制灰盒 → 烘焙为 `TerrainGrid` → 编辑器校验（出生点、路径、锚定、可爆物密度、救援点可达）→ 生成关卡资产。
- 角色：Aseprite/自绘像素帧导出图集；统一 pivot、像素密度、动作帧表；禁止把非整数缩放图导入。
- 敌人/道具：优先复用动画状态机与数据定义，不为每关写专用脚本。
- 特效：短生命周期、对象池、同材质合批；碎片必须来自图集。
- 音频：原创/可商用授权；低频冲击+中频碎裂+高频金属三层；慢镜头只改总线，不重录。
- 关卡设计检查：每关首次通关 60~120 s；至少 1 条非唯一解法的破坏路径；检查坍塌后不会卡死/无法返回。
- M2 开工前冻结 4 角色与 3 关的内容表格；M1 结果决定是否需要简化机制，不在 M2 中途加新角色/新模式。
